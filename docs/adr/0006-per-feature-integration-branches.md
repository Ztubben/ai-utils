# Per-Feature integration branches with completion-time history rewrite

Previously every green story merged straight into the base branch (default `develop`), so parallel Features interleaved their commits and half-finished Features leaked into `develop`. We now integrate per Feature: a Feature's stories merge into **one feature branch**, and `develop` receives the Feature only when it is complete. Orphan Stories keep the old flow (own story branch, direct merge to `develop`).

> **Amended (PRD #69).** The decision to integrate per Feature stands; its *topology* was wrong. Originally a Feature's stories shared one working branch and, later, one marked pull request. The Story remained the unit of work, of model assignment and of review, but the pull request became the unit of everything the negotiation machinery counted — and the two units no longer lined up. Sections marked **Amended** below carry the corrected shape; the original reasoning is kept because it is still why per-Feature integration exists.

## Decisions

- **One integration branch per Feature; one working branch and one pull request per Story** *(amended, PRD #69)*. The feature branch is still deterministically named from the PRD issue (`feature/{issue}-{slug}`, same `branch_name` machinery as story branches) and still created lazily off `develop` — now the first time one of its Stories opens a pull request, so a Feature costs nothing until its first Story starts. Every Story, Orphan or Feature, works on **its own** story branch and carries **its own** marked pull request; only the base differs, an Orphan Story's targeting `develop` and a Feature Story's targeting its feature branch. A Feature Story's branch is cut from the current feature tip, so it starts from what its predecessors landed. Implementation-green pushes that branch, opens or updates that pull request, and moves the Story to `state:in-review`; neither AFK nor HIL implementation-green merges, closes, or enters awaiting-bench.

  *Why the shared pull request failed.* Round budget and review context were both counted over the pull request. The second Story of a Feature therefore inherited every Round the first had spent — in a live deployment a Feature's third Story escalated to a human at `spent >= max_rounds` with **zero** Rounds against it, never having been reviewed once, and raising the limit could not fix a count cumulative for the Feature's whole life. The bundle had the same shape of problem: a round's diff is the pull request's base-to-head range, so each Story's reviewer was handed every earlier Story's changes too, growing with every Story that came before. With one pull request per Story the diff *is* the Story's change, and the round limit means what it says.

- **Story completion is uniform** *(amended, PRD #69)*. A green, reviewed Story merges its own pull request into its own base per `branching.afk_merge` and deletes the branch: into `develop` for an Orphan Story, into the feature branch for a Feature Story. An AFK Story closes there as Passing. A HIL Feature Story merges on the same terms and moves to Awaiting Bench Verification, so the Stories after it can build on its code; a HIL Orphan Story is not merged before verification, because nothing stands between it and `develop`.

- **The physical gate sits at the Feature boundary** *(amended, PRD #69)*. Because unverified HIL work now reaches the feature branch, the completion pass refuses to integrate a Feature into the base branch while any HIL Story of that Feature is still open, and names each one. Unverified hardware code reaches the feature branch, never `develop`. Bench verification remains a human closing the HIL Story.

- **The Feature integration pull request is not model-reviewed.** Every Story it contains was reviewed on its own pull request; re-reviewing the union would spend invocations re-litigating settled findings. It therefore carries no `ralph/model-review` check, which is why `enforce_admins` stays false on a protected base branch.
- **Branch invariant + reset-on-block** *(amended, PRD #69)*. The feature branch contains only reviewed, merged story work: no story's WIP ever reaches it, because every story works on its own branch. Reset-on-block therefore has nothing to rewind and nothing to rescue — a blocked story's work is quarantined from its siblings by construction. What remains is the part a branch cannot do: push that branch so a human can reach it, describe the failure and name the branch in the demotion comment, and move the story to `state:blocked`. The rescue branch, the recorded feature-branch boundary, and `branching.rescue_pattern` are gone.
- **Commit-anchored bench verification.** The human verifies a HIL story at its recorded completion commit, in commit order — never at the moving tip — so sibling stories may continue landing on the branch while a HIL story awaits bench without making the bench verdict ambiguous. The anchor names the exact reviewed commit and how to fetch it (`git fetch origin refs/pull/N/head`), because the story branch is deleted on merge. Bench-pass = close the issue. Bench-fail = comment observed behavior + flip to `state:ready`.
- **Fix forward as fixups; rewrite history only at completion.** Ralph repairs a bench-failed story as `fixup!` commits of the story's completion commit — since PRD #69, on a fresh story branch merged into the feature branch like any other Story's work — never by mid-feature rebase, which would invalidate outstanding bench anchors and force-push under the human's feet. History rewriting is free at feature completion (all stories closed ⇒ all anchors dead), so that is the single rewrite point. Humans may rebase the feature branch at any time; Ralph therefore hard-syncs it from origin at every iteration start.
- **The completion pass** runs at tick time (the final close of a HIL Feature is a human act Ralph cannot observe at story time). For each `prd`-labeled issue with `state:ready` and ≥1 story, all closed: (1) `rebase --autosquash` to collapse fixups into their story commits — on conflict, abort and keep the linear history (cosmetic degradation only); (2) rebase the cleaned branch onto current `develop`; (3) run full gating — the Feature has never been tested against this `develop`; (4) open the Feature PR and merge it **itself** with a merge commit (never squash), then close the PRD. A conflict in (2) or red gate in (3) is a Feature-level blocker: push the branch, comment details on the PRD, label it `ready-for-human`, move on — it does **not** trip the `needs-human` circuit breaker, because independent feature branches don't poison each other.
- **History policy:** `develop` keeps unsquashed per-story commits with one merge commit per Feature; squashing happens only at the human-owned `develop → main` promotion.
- **Freshness on out-of-Feature deps.** When starting a story that depends on an Orphan Story or a PRD (work that landed in `develop` after the feature branch forked), Ralph first merges current `develop` into the feature branch — a merge, not a rebase, so bench anchors survive; the completion-pass rebase linearizes it away later.

## Considered options

- *Per-story branches + PRs into the feature branch*: rejected in the original decision — PR sprawl was the problem being solved. **Adopted in the PRD #69 amendment**: sprawl is the cost of making the Story the unit of the pull request, and it is the cheaper cost. A shared pull request made the Round budget and the review diff belong to the Feature while every other unit belonged to the Story, and no amount of tuning reconciles that.
- *Freeze a Feature while any story awaits bench*: rejected — commit-anchored verification preserves bench isolation without stalling the Feature.
- *Rebase the fix into the faulty commit immediately on bench-fail*: rejected — invalidates every outstanding bench anchor and races the human's own rebases.
- *Squash-merge the Feature into `develop`*: rejected — per-story history in `develop` is wanted; squashing belongs at `develop → main`.


## Migrating a Feature already in flight

Adopting the amendment does not rewrite anything automatically, and no in-flight pull request is retargeted for you.

1. **Configuration.** Remove `branching.rescue_pattern` from `.ralph.yml`; it is no longer a schema key and `ralph --check-config` will name it. Nothing else changes — the story branch pattern and the feature pattern keep their meanings.
2. **Any Feature with a shared, still-open pull request.** Close it by hand, or retarget it if you want its commits to land on the feature branch as one piece. Either way its Stories keep whatever they already merged; the feature branch is the record.
3. **Remaining Stories of that Feature.** They pick up the new topology at their next start: a branch of their own cut from the current feature tip, and a pull request of their own into the feature branch. Nothing has to be re-implemented.
4. **Stories already In Review under the shared pull request.** Finish or close their negotiation before adopting, or let them escalate and arbitrate by hand — their recorded rounds are read from the Story issue, so a Story mid-negotiation is not stranded, but it will still be judged against a diff that includes its predecessors until it opens a pull request of its own.
5. **Branch protection is unchanged.** The base branch keeps requiring CI and `ralph/model-review`; a feature branch needs no protection of its own.
